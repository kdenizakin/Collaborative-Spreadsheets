\section{General Information}

In this research, the aim is to build a collaborative spreadsheet that supports formula parsing like Microsoft Excel.
React.js and TypeScript are used to build the application. 
Typescript is chosen instead of Javascript because it provides strict typing.
Synchronization across multiple clients was achieved by Yjs
which is a JavaScript framework that uses Conflict-free Replicated Data Types (CRDTs) 
with an abstraction of shared data \cite{yjs}. Zustand is used for global React state management. 
Real-time updates are transmitted to the connected peers using a WebSocket layer which is implemented by y-websocket.

\section{Related Work}
\subsection{Semantics for CRDT-based Collaborative Spreadsheets}
Our research builds upon the work of \textcite{yanakieva2023study}. In their work, they compared several data models 
on implementing collaborative spreadsheets and proposed an implementation
which supports conflict resolution for offline operations using a combination of existing replicated data types provided by Yjs. 
They proposed a new data model called "Fixed Elements (Remove-keep)" to prevent data loss when a user modifies a cell and, 
at the same time, another user deletes the corresponding column or row. 
They did this by using two y-arrays (to keep track of the orders of cell IDs), a y-map (to associate cell IDs to their contents) 
and two "keep" y-maps for columns and rows. 
The idea is to store the "keep" IDs in these maps when there is a "positive update" on a cell.
If there is a removal operation concurrent to the positive update, the "keep" IDs are used to undo the removal operation. 
Y.UndoManager was used to implement the undo operation.
This implementation is used in our research as well. 
Update-wins CRDT for cell content and formula support is also implemented in our research which was not present in the original work. 


\subsection{AegisSheet: A Compositional CRDT for Collaborative Spreadsheets} \par

Another relevant work is AegisSheet, which uses a composition of CRDTs for collaborative spreadsheets. 
It was implemented by \textcite{pfeil2026aegissheet}. Their implementation involves conflict resolution for:

\begin{itemize}
    \item Concurrent cell edit and column/row deletion as similar to the approach used in the work of \textcite{yanakieva2023study},
    \item concurrent cell edits by using Multi-Value CRDTs (allowing user to select the desired value),
    \item concurrent cell edit and column move,
    \item concurrent range creation and column deletion.
\end{itemize}

In their implementation, rows and columns were stored using identifiers and 
cell content was stored in a map with keys following orders of row/column ID pairs. 
In this form, it carries similarities to the previous study as well as to our own study.

Their implementation also supports moving columns/rows and an undo feature (which are not implemented in our research).
As demonstrated by \textcite{kleppmann2020moving}, standard list CRDTs encounter duplicate elements 
when moving elements concurrently because move operation requires to delete an element from one position and insert it into another.
Therefore, in order to handle this issue, they created a new CRDT called "ReplicatedUniqueList".


They didn't address formula support in their implementation.

\subsection{Conflict-free Replicated Spread Sheets}
\textcite{sypytkowski2023crdttables} proposed an implementation of a collaborative spreadsheet named as "Conflict-free Replicated Spread Sheets".

In his implementation, in comparison to our approach, he didn't use Yjs framework. Instead, he implemented the spreadsheet using
standard arrays and LSeq data structure. 

He stored spreadsheet data in a single table. This table was constructed as an array of rows, and each row was an array of cells.
Each cell carries last-writer-wins semantics. To do this, there is companion 'versions' table containing timestamps for each cell.

In order to keep track of the order of rows and columns, 
he used LSeq data structure because using a standard array structure does not provide a way to maintain the order of elements in a collaborative environment.
For example, with a standard array, if two users concurrently insert elements at the same index, the order of these elements will be lost. 
The idea behind of LSeq is "Fractional Indexing". Fractional Indexing is an approach which assigns IDs to each of its elements.
When a new element is inserted between two elements, the real-number averages of the two elements should be calculated for the new element's ID. 
With this way, eventual consistency is guaranteed in every replica and there is no need to shift remaining elements.
In the implementation of \textcite{sypytkowski2023crdttables}, these IDs are a combination of sequence of bytes (e.g. byte[]) and the ID of the replica. 
These sequences are used to order elements with lexical ordering.
When a new element is inserted, it is assigned a new ID that is lexically between the IDs of its neighbors. 
For example, if there are 2 elements with IDs 'a' and 'b', a new element would be assigned an ID that is lexically between 'a' and 'b' (e.g. 'ab').

His implementation consists of 4 main operations:
\begin{itemize}
    \item Insertion of columns/rows. Each insertion operation assigns a timestamp to each cell which is called as 'version timestamp'. 
    \item Update: What is interesting about this operation is that 
    it expands the table if the user tries to update a window 
    that is out of the current table's bounds.
    This approach prevents the loss of updates; 
    otherwise, if the table does not expand to apply updates, 
    and if a table updated by one user is larger than the one belong to the other user, 
    updates falling outside the dimensions of the smaller table would be lost.
    Each update operation assigns a timestamp to each cell which is called as 'version timestamp'. 
    \item Delete: Each delete operation has a timestamp as well. Before any deletion of a column/row, all cells on to be deleted row/column are iterated 
    and the 'version timestamp' of a cell is compared with the deletion timestamp.
    If the version timestamp is greater than the deletion timestamp, it means there is a concurrent update operation of a cell. 
    In this case, deletion is not performed.
    If that's not the case the cell value is set to null.
    If the column/row has only null values left, then it is deleted from the table.
    \item Selection: To select a window of cells. This operation consists of a set of applications such as formula ranges (e.g. SUM (A1:B2)), 
    applying a set of formatting attributes to multiple cells, merging cells and preventing displayed content to be changed unexpectedly 
    when there is a copy/paste operation from another user. As he mentioned, this operation comes with a problem of concurrent row/column addition or deletion. 
    For example, if a user selects a range of cells (e.g. SUM (A1:B2)) and another user deletes a column/row in that range, the range will differ from our initial selection.
    To address this issue, he proposed a solution that is based on the idea of logical indexing. Two opposite points of the intended selection are represented as
    logical indexes. These indexes are again implemented with LSeq data structure. 
\end{itemize}

In his blog, \textcite{sypytkowski2023crdttables} mentioned some optimizations as well. Such as "Indexing Selections" using R-Trees for selections 
in order to listen to changes in the selected cells and recalculate formulas accordingly. However, he didn't implement this feature, and later he mentioned that 
benefits are negligible compared to the brute-force selection of cells.

\section{Representing Spreadsheet Data in Yjs}

\subsection{Overview}
Representing spreadsheet in a collaborative environment was quite straightforward. 
Yjs framework was very useful because it abstracts all the network broadcasting messages, 
CRDT implementations, merging updates with CRDTs, and even WebSocket connections. 
Therefore, none of these aspects are needed to be reimplemented. 
However, using this framework with React's state management was the hardest part 
because Yjs only solves synchronization between other clients not how the client's screen is updated 
and how does the data is displayed. 
In relevant sections this will be explained further.  

The implementation uses 2 arrays and a map. These arrays store cell IDs and are crucial to display them on the table with respect to the order. The map is used to store the content of the cells. This means there is no global grid, which might cause bottlenecks during adding/removing columns/rows so, instead of storing the entire table as a matrix, the sheet is stored into separate structures.

\subsection{YColumns \& YRows (SpreadSheet.tsx)}

These are CRDT-based arrays that are responsible for ordering cells in the spreadsheet. 
Using a map structure is not enough to ensure ordering, because maps are unordered. 

They appear in the SpreadSheet.tsx component. 
In this component, YColumns and YRows are used to transfer cell IDs to the Spreadsheet's React State when this component is mounted. 
Later, 'columns' and 'rows' states are used in the table to display the content. 
They show how the spreadsheet synchronizes the Yjs shared column data with the local React state. 
Because Yjs data structures live outside the React state, changes in Yjs do not trigger a re-render in the user interface (as mentioned before). 
An observer function inside 'useEffect' bridges this gap. When a user adds or removes a column, the observer function receives an event: 

\begin{itemize}
    \item Insertions: When new column IDs are inserted, their target index is found using 'findYArrayElement' function. 
    The new column is inserted into the local 'columns' array.
    \item Deletions: Deleted column IDs are collected from into a data structure. Then the local React state is then updated by filtering out these deleted columns.
\end{itemize}

\subsection{YMap (Cell.tsx)}

To keep values of each cell, YMap structure was used. It's a CRDT-based key-value (Yjs provided abstraction for CRDTs as mentioned) 
pair where IDs are defined as: \\ \verb|let cellId: string = `${col.id},${row.id}`;| \\ and contents are just texts. 
To use the YMap effectively, for every Cell on the spreadsheet, an observer is defined. 
This observer is responsible for keeping track of the remote updates of the Cell's own content. 
This comes with a performance cost, but the benefits are not negligible and was the most convenient approach so far rather than using a global grid. 

First, with this approach, storing Cell components in a global grid was not needed. 
If there was a global grid, adding or removing rows/columns would be costly because of shifting all the remaining elements.

This observer also has an implementation for Update-Wins CRDT. 
The idea behind it is to store updates that are concurrent to each other (e.g., offline clients performing updates) and merge them by concatenation. 
That's the reason why YMap entries have arrays as their values. 
Later appendConcurrentUpdates() is called to do string concatenation (merging concurrent updates).

\subsection{YColKeep \& YRowKeep (SpreadSheet.tsx)}

With the standard Yjs, data was lost when a user modified a cell and, at the same time,
another user deleted the corresponding column or row. 
To solve this problem, this implementation uses the idea of 'keep' arrays which has been proposed by \cite{yanakieva2023study}. 
This structure prevents data loss mentioned above. 
The solution involves storing a "keep ID" for each cell that is being modified. 
When there is a positive update on a cell: "keep ID" \\ \verb |let keepId: RemoveKeepOperationId = `c${YDoc.clientID as number}.${1 as number}`;| 
is stored in those arrays. Clients monitor the changes of arrays with observers, and if they are non-empty, 
undo operations are performed equal to the number of elements in the array structures.

\section{Formula Support}

\subsection{Information}

Supporting formulas in a collaborative environment would be interesting for several reasons:

\begin{enumerate}
    \item Retrieving spreadsheet data for formula calculation. 
    What is the feasible way of doing this without ruining the spreadsheet if there are offline users too?
    \item Prevention of circular referencing during calculation and recalculation.
    \item Reactivity of the formula cells. When a formula is defined, the corresponding cells are marked. 
    When there is an update on these marked cells, the formula should be recalculated and the result should be displayed in the formula cell.
    \item Shifting ranges of cells when a new row or column is added before or above the cell that stores 
    the range of cells, or when such a row or column is deleted. 
    \item Concurrent row/column addition and deletion between range of cells that are used in a formula.
    \item Formula recalculation for every update and its probable bottlenecks. 
    For example, let's say a result is computed for a formula using 10000 cells and 
    a user updates one cell value by incrementing it by one. 
    In this scenario, should the formula be calculated from the very beginning, 
    or is it possible to support this functionality more efficiently? 
    While the current implementation does so by recalculating the formula, 
    implementing more efficient algorithms is possible.
\end{enumerate}

This implementation addresses the first 5 points. The last point is not implemented yet, but it is a possible future work.

\subsection{Implementation Details}

In this section, relevant parts of functions/components for formula calculation will be explained.

\subsubsection{Formula Parser}

First, the \texttt{`fast-formula-parser`} \cite{fastformula} library is used for formula functionality. 
With this library, my implementation supports basic arithmetic operations, cell references, and range references.
The main implementation for this library is in 'Formula.ts'.
This class is responsible for parsing the formula, detecting circular references, and recalculating the formula
when there are updates on the marked cells. A pop-up is displayed when a circular reference is detected. For this,
\cite{sweetalert2} library is used.

This class has several attributes, which are: 'formula', 'cellId', 'position', 'formulaResult', 'markedCells', 'operation', 'leftBoundaries', and 'rightBoundaries'.
Attributes for left and right boundaries are used to store the leftmost and rightmost cell row and column names in a formula range (e.g. SUM(A1:B2), left boundary: A1, right boundary: B2).
They are stored in a priority queue because when a new row or column is added in between the left and right boundaries (even concurrently), 
the left and right boundaries should be updated by peeking priority queues. 
For example, if the formula is SUM(A1:B2) and a new column is added between A and B, the new formula should be SUM(A1:C2). 
To implement a priority queue, the implementation of \textcite{aissi2024priorityqueue} was used. 


There are functions in this class which are: 'parser()', which comes from the library itself, and 'parserDriver()' 
which calls the parser() with 'spreadsheetData' obtained in the Spreadsheet component. 


This parserDriver() function returns the formula result and returns the IDs of the cells that have been marked 
(or registered) while computing the formula result.


\subsubsection{Spreadsheet Store}

To retrieve the store globally, Zustand, which is a small, fast, and scalable state management solution \cite{zustand}, is used. 
It is like Redux but was easier to implement.

Normally, the direction for the data transfer is from the parent to the child. 
However, it would not have been feasible to transfer all spreadsheet data from the Spreadsheet component to every Cell.
The second solution requires spreadsheet data*num of total cells. 
With Zustand, there is a single spreadsheet used for formula calculations.

'spreadSheetData' is the name of the object that contains all values in each cell and is a matrix of strings obtained from 'SpreadSheetStore.ts': 'returnSpreadSheet()'. 
As mentioned in section 3.1 this function returns all spreadsheet data (optimization might be possible).

\subsubsection{SpreadSheet Component}

The SpreadSheet component provides a table by implementing the PrimeReact library's DataTable structure with the Yjs framework. 
While the table's rows and columns are tracked via Yjs arrays (yRows, yColumns), 
observers ensure that all additions and deletions are reflected in the local React state. 
When a new row or column is created, the corresponding cells are automatically created in the shared map, 
and deletion operations trigger both map cleanup and undo mechanisms. 
This component also consists of other components, which are headers (ColumnHeader), cells (Cell), and buttons.

\subsubsection{Cell Component}

\paragraph{handleFocusOut()}

Formula cells register candidate cells in the 'markedCells[]' array when the formula is defined to compute the result. 
Similarly, candidate cells store IDs of the formula cells in the 'formulaReferenceCells[]' array. 
This is an array because there might be multiple formula cells registering the same cell. 
These 2 arrays are kept in every Cell component and are defined in 'CellType'. 
Arrays are optional, denoted with "?", so it is not a problem if they are undefined.

After these operations, the 'handleFocusOut()' function in the Cell component is responsible for the formula recalculation. 

\subsection{Circular Reference Handling}

A circular reference occurs when a formula refers directly back to its own. This creates an endless calculation loop. 
For example, if cell A1 contains the formula SUM(A1+B1), then A1 references itself. 

The implementation does not produce an endless loop in the definition of a formula range phase. 
Neither does formula recalculation because it does not use observers.
Rather, it is being done via the `handleFocusOut()` function in the Cell component.
Therefore, a formula is calculated via `handleFocusOut()` calls. 
Even though there are no calculation infinite loops, when a user wants to increase a cell value by one 
(if the cell is marked and the formula is SUM), as in a circular reference case, formula cells register themselves, 
the existing result from the previous step, so it does not increase by one rather formula's previous result + 1. 
This produces a result that the user does not intend.

To solve this, Microsoft Excel's approach is used. When it detects a circular reference, 
the formula value is set to 0 and a popup message is displayed to the user as displayed in Figure~\ref{fig:circularrefsweetalert2}.
This implementation uses a very basic approach with a simple loop.
